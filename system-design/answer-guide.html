系统设计答题格式

把它当作口头表达顺序，而不是必须填满的表格。先围绕题目的主要矛盾讲透，再补相关细节。

推荐顺序（30–40 分钟）

阶段回答什么可用句式
1. 澄清需求
约 3–5 分钟		用户、核心用例、暂不覆盖的范围、成功标准。“我先确认：任务提交后需要立即返回 ID，结果允许异步获取，对吗？”
2. 估算规模
约 2–3 分钟		粗估峰值请求量、数据量、延迟和保留时间。数字来自题目；没有数据就声明假设。“先按峰值每秒 100 次提交、平均任务 2 分钟估算，并发约 1.2 万。”
3. 接口与数据
约 3–5 分钟		关键 API 或事件、核心实体、状态机、数据由谁持有。“POST /jobs 返回 jobId；任务状态从 queued 到 running，最终进入 succeeded 或 failed。”
4. 架构与主流程
约 8–10 分钟		画出入口、存储、队列、执行节点与外部依赖；沿一条请求说明写入和读取。“先持久化任务，再派发给执行节点；节点返回结果，由任务服务提交终态。”
5. 异常与一致性
约 5–7 分钟		超时、重试、重复请求、进程重启、数据竞争；说明至少一次与恰好一次的取舍。“投递可能重复，所以结果写入以 jobId + 阶段为幂等键。”
6. 运行与演进
约 3–5 分钟		监控、容量、限流、安全和成本；指出瓶颈、备选方案与改造顺序。“先观察排队时长和执行成功率，再决定是否按任务类型扩容。”
7. 追问面试官改动约束时，更新图和取舍；说明哪些原先假设失效。“如果节点会运行 30 分钟，恢复策略要从重跑改为 checkpoint。”

简短示例：设计异步任务平台

这是表达格式示例，不是所有题目的标准答案。

需求：提交后立即返回任务 ID；可查状态；失败可重试。暂不支持任务间依赖。
规模：假设峰值 100 次提交/秒，任务平均运行 2 分钟，需先估算并发容量。
接口：POST /jobs（带幂等键）、GET /jobs/{id}、POST /jobs/{id}/retry。
数据：Job{id, type, status, attempt, owner, resultRef, updatedAt}；状态变更受版本号约束。
图：客户端 → API/任务服务 → 数据库 + 队列 → Worker → 结果存储。
主流程：先提交任务记录，再投递；Worker 领取后更新运行状态，结果先落盘再提交终态。
异常：消息可能重复，写结果用幂等键；Worker 失联后按租约超时重新派发。
运行：监控队列等待时间、失败率、重试率；按任务类型限流和隔离。
取舍：先用至少一次投递 + 幂等写入；如果外部副作用无法幂等，要增加人工核对或补偿。

像人工评审、经验缓存、消息队列、强一致事务，都只在题目需要时展开。答不出的地方先写假设和验证办法。
